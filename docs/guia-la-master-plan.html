01 / Mandate

Why we're building this—and why we're starting again.

The original Cotiju app started as a practical tourism guide for Cotijuba, Pará. It became a valuable proof of concept, but its feature count, Supabase coupling, parallel caches, complex permissions and unfinished integrations outgrew what a tiny team can reliably maintain. We want to keep the learning and leave the accidental complexity behind.

guia.la is not “Cotiju, rewritten.” guia.la is a sustainable platform for destinations with distinct geography and services. Cotijuba is our first real deployment and field test—not an architecture hardcoded for every future location.

Identity and naming: guia.la is the reusable white-label platform and intended public brand/domain (registration and DNS are not yet confirmed by this document). Cotijuba is the first destination and pilot configuration. Cotiju / cotiju-app refers exclusively to the existing legacy proof of concept and its private GitHub repository, not the new platform. New repository, package scope, app bundle IDs and store names must be decided and verified separately; do not assume ownership of a domain, app-store name or handle.

What we optimize for

Small team, growing reach

  • One shared core for web, Android and iOS, with native exceptions only where justified.
  • Fast onboarding for destinations, not bespoke engineering each time.
  • Verified local content, community ownership and practical information.
  • Low predictable infrastructure and operational cost.
  • Agent-driven delivery with automated, inspectable quality evidence.
What we intentionally avoid

Complexity disguised as flexibility

  • Copying the v1 schema, services or auth system wholesale.
  • Three separately maintained apps before evidence demands them.
  • A marketplace or dynamic plugin loader in v1 of the platform.
  • Accounts required to read public destination information.
  • Unverified schedules, made-up data or silent stale fallbacks.
  • Running every expensive native build on every trivial PR.

02 / Legacy lessons

Preserve the knowledge. Audit the data. Don't inherit the mess.

The existing private repository luandro/cotiju-app remains the reference implementation and source of historical decisions. It must not become a dependency of guia.la, and its live data must never be rewritten by an unreviewed migration.

Extract & adapt

High-value ingredients

  • Domain models: places, categories, media, boat timetables, guides, moto-taxis, events and permissions.
  • Verified place coordinates, licensed photos, user-facing copy, translations and assets.
  • Useful flows: maps, offline experiences, location details, local contact actions and administration.
  • Existing Vitest/Playwright cases and known bug reproductions.
  • Offline, freshness and timezone lessons; test fixtures from failures.
Reconsider / do not copy

Known liabilities

  • Supabase-specific query hooks, auth/realtime context, row-level policy assumptions.
  • 24-table migration design as a presumed minimum viable schema.
  • Multiple overlapping caching layers and indefinite spinners.
  • 2025-only fallback tide data, inconsistent transport day/validity handling.
  • Routes and features with incomplete implementations; stale docs.
  • Secrets, private profile records and media without confirmed rights.

Legacy extraction is a dedicated delivery phase (01), not a migration script. For each asset record provenance, ownership, freshness, consent/licensing, current correctness, destination applicability, and a decision: reuse concept / adapt code / migrate data / archive / discard. Confirm backups and inventories before touching production.

Reference points to review: production incident #63, public data audit #59, transport validity #64, PWA cache security #65, unmerged Cloudflare D1 research PR #39, earlier rebuild architecture RFC #71. Issue states may have changed; re-check at implementation.

03 / Architecture

A thin core with genuinely independent features.

For guia.la, the default technical direction is an Expo/React Native universal shell, React Native Web, an explicit widget composition step, and a small Cloudflare backend. It is a working hypothesis to validate, not permission to start a multi-month rewrite without proof.

Proposed foundations
  • Expo + Expo Router: native-first navigation with web support.
  • TypeScript + React Native Web: shared UI and domain behavior; platform files for truly different components.
  • Cloudflare Workers/Hono + D1/Drizzle + R2: small, testable service boundary.
  • Admin interface: minimal editorial tools; no visitor login by default.
  • GitHub Actions + EAS + Playwright + Maestro: reproducible web/native quality evidence.
Hard architectural constraints
  • No widget may import another widget's private implementation.
  • Every public API response has explicit error and freshness semantics.
  • Tenant-scoped reads/writes are checked on the server; D1 has no PostgreSQL RLS.
  • Private resources must not enter shared offline/service-worker caches.
  • Maps may use separate *.web.tsx and *.native.tsx implementations.
  • Web share pages must pass HTML/OG tests without relying on JavaScript execution.
04 / Composition

Build only what the destination needs.

A widget is a versioned, testable feature package—not necessarily a tiny homepage card. It can contribute a card, route, map layer, editorial form and backend schema. Beaches and waterfalls should generally share one configurable Places domain; transport services similarly share reusable primitives.

Two gates, not one: build-time inclusion controls imports, routes, JavaScript bundles and optional native packages/permissions; runtime flags control ordering and visibility of code already compiled. A multi-destination flagship app will contain the union of features needed by its destinations; a partner-specific build can exclude more.

05 / Delivery phases

Eleven verifiable checkpoints. No invisible progress.

Each phase ends in a reviewable artifact and a defined exit gate. Automation begins in the first build, becomes more stringent over time, and retains evidence that another agent can re-check. Phases are sequential for planning but independent work may run in parallel after contracts are stable.

Select a phase to inspect scope, QA and exit gate

07 / Agent operating model

Autonomy without undetectable damage.

The agent should work autonomously on bounded, reversible tasks and produce evidence that makes reviews fast. It should not treat permissions to write code as permissions to modify production data, ship store releases or approve its own security exceptions.

Autonomous by default
  • Read architecture, goals, phase plan, widget contracts and previous work state.
  • Pick/plan a bounded task with explicit acceptance criteria and dependency checks.
  • Implement on a branch, add relevant tests/stories and create a preview.
  • Run the affected build/test matrix, inspect screenshots/logs and self-correct a bounded number of times.
  • Publish a PR with summary, evidence, risks, docs changes and the next unblocked task.
Human approval required
  • Production data migration, deletion or modifying existing user records.
  • Secrets, cloud credentials, permission escalation or security policy relaxation.
  • Changes to tenancy/auth boundaries, privacy policy or licensing choices.
  • Store publication, billing changes, paid services and public domain cutover.
  • Disabling required checks, removing tests or declaring an unverified feature production-ready.

Source of truth: Git-tracked AGENTS.md, SPEC.md, docs/architecture/, docs/roadmap/ and widget contracts. HTML files are human-friendly presentations of the plan; Markdown/JSON are the maintainable machine-readable instructions. Keep them consistent.

09 / Handoff

What the reviewing agent should do next.

First: review. Second: generate the phase playbooks.

This document is master plan version 0.2. The paired file guia-la-agent-handoff.md tells an agent how to challenge this plan, check current upstream dependencies and the original Cotiju repository, then generate complete, individual HTML playbooks for phases 00–10 with executable QA and acceptance gates.

No code migration or production mutation is authorized by this artifact. If evidence changes a technical recommendation, record the trade-off in a decision note. If access to GitHub, EAS, Cloudflare or source data is unavailable, state the blocker instead of fabricating findings.

Expected planning outputs
  • planning/index.html — navigable phase index
