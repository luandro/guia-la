Phase 02 — Bootstrap Expo universal monorepo with a walking skeleton

Create the pinned SDK 58 Expo Router workspace that builds one reference Places journey from fixtures on web, Android and iOS — and prove raw-HTML SEO on the static web export (spike S1).

Status: draftHigh (foundational)Builddepends on: 00

Phase 02 turns the guia.la platform from documents into a building repo. Per the review's proposal (§8 edit 1, review.md), this phase absorbs two things the master plan originally deferred: the SEO spike S1 (the riskiest web assumption) and a walking skeleton — one real Places list/detail journey over fixture data — so the first end-to-end slice exists before infrastructure phases 03–06 deepen.

Everything here runs free and local first: no paid cloud builds (that is Phase 04b), no backend (Phase 07), no store submission (Phase 10). Native verification is honest about hardware: if no Apple hardware or EAS account is available, the gate records the exact blocker instead of pretending.

Why this stage exists

The stack choice — one Expo/React Native codebase for web, Android and iOS — is still a hypothesis until it builds and boots from this repo (decisions D-02). The review verified versions and documentation (expo-stack §1) but nothing was run; that is precisely what this phase is for.

The riskiest single assumption is SEO: Expo Router's static output promises per-route HTML with OG tags emitted by generateMetadata(), but dynamic routes need generateStaticParams (so every published place requires a re-export), the SDK 58 docs contradict themselves on the default web.output, and <Head>-based patterns from older tutorials silently stop working in static HTML (expo-stack §1.3). Moving S1 here — proposed in review §8 — means the go/no-go evidence for D-03 exists before any content architecture is built on top of it.

The walking skeleton exists because of the legacy lesson: Cotiju's home page waited on empty database tables and spun forever (legacy #60). guia.la's first screen is therefore fed by local fixtures with explicit loading/empty/error states wired from day one — the failure modes are part of the skeleton, not an afterthought.

  • Route and metadata contract (illustrative):
// illustrative — apps/app/src/app/places/[slug].tsx
import type { Metadata } from "expo-router/server";

export function generateStaticParams() {
  return allFixtures().places.map((p) => ({ slug: p.slug }));
}

export function generateMetadata({ params }): Metadata {
  const place = placeBySlug(params.slug);
  return {
    title: `${place.name} — guia.la pilot`,
    description: place.summary,
    openGraph: { title: place.name, description: place.summary },
  };
}
  • Patterns adopted deliberately: explicit web.output: "static" (never

rely on the contradictory default, expo-stack §1.3); generateMetadata() for OG and never the SDK 58-broken <Head> pattern (migration notes); env access only through a zod-validated config module; states-first data loading (every async view renders loading, empty, error).

  • Forbidden in this phase: cloud accounts, CI credentials, paid builds,

real Cotijuba content (fixtures only), any second journey (tides, boats, maps), native config plugins beyond the template set, secrets or API keys anywhere (there is no consumer yet), adopting Ignite/Obytes/T3 templates (review R13) — patterns are hand-ported, not inherited.

  • Security/privacy implications: nothing secret exists to leak yet, which

is the point of doing this phase before a backend: the secret-handling habits (no values in configs, no keys in client env) are set while the cost of enforcing them is zero. Atlas/source-map outputs from bundle analysis contain inlined env values and are treated as secret artifacts, never committed (expo-stack §1.9).

  • Acceptable alternatives: Next.js web + separate RN app (fallback per

review §1 only if S1 fails — two rendering stacks, the thing this platform exists to avoid); web.output: "server" via the undocumented workerd adapter (rejected — "no continuous tests" warning in the Expo docs); Expo Hosting free tier instead of Cloudflare (possible, but custom domains are paid and the review recommends Workers Static Assets).

Visual and functional QA

Preview patterns that are real in this phase: local only — http://localhost:8081 via npx expo start, and the exported dist/ served locally (for example npx serve dist). Remote preview patterns are TBD in Phase 04.

  • Human journey (web): clean clone, run the README commands, open the

local preview, walk list → detail → back; force each state (empty fixture set, malformed fixture, offline via devtools) and confirm a visible, labeled state — never a spinner with no deadline (legacy #60 is the anti-example).

link-preview tool (or WhatsApp draft) from the locally served export and confirm the card shows title/description — this is the human version of S1.

  • Agent journey: from a clean clone, reproduce the export and re-run the

OG assertions; then delete one fixture place, re-export, and confirm the detail page for it is gone while others remain.

Automated verification

Markers: validated = the command/mechanism is verified in the research files (still to be run on guia.la code); proposed = invented for this repo, flags may need adjusting at first run.

# proposed — scaffold (template alias re-check is part of the task; S11)
npx create-expo-app@latest apps/app --template default@sdk-58
# proposed (inference) — doctor and pin checks follow the recommended CI
# pattern ([expo-stack §2.7](../research/expo-stack.md)); not run in research
npx expo-doctor
npx expo install --check
# validated — static export is the documented mechanism; source-map mode's
# flags were verified via --help ([expo-stack §1.9](../research/expo-stack.md))
npx expo export -p web
npx expo export -p web -s external
# validated — Atlas bundle listing exists and writes .expo/atlas.jsonl;
# the artifact is SECRET (inlined env values) — never commit it
EXPO_ATLAS=true npx expo export -p web
# proposed — S1 raw-HTML assertions (the spike's core check). Expected:
# every grep finds its tag; a miss prints the file and exits 1.
test -f dist/index.html || exit 1
for f in dist/places/index.html dist/places/*.html; do
  grep -q 'og:title' "$f" || { echo "$f"; exit 1; }
  grep -q '<title>' "$f" || { echo "$f"; exit 1; }
done
  • Deliberate-failure demonstration 1 (evidence in PR 02-8): remove generateStaticParams from the detail route and re-export — the expected observable is dist/places/<slug>.html missing from dist (or the assertion failing), proving the S1 check can actually fail.
  • Deliberate-failure demonstration 2 (evidence in PR 02-8): unset a required env var and run the build — the expected observable is an immediate, named-variable failure from the zod guard, not a runtime surprise later (a pattern legacy PR #52 proved valuable).
  • Positive + negative pairing: every assertion above has a demonstrated

failure mode or is paired with one in PR 02-8; a check that has never failed is not yet evidence.

Acceptance gate

Gate

Phase 02 passes when a clean clone reproduces the web export and

its raw-HTML OG assertions, the skeleton shows all four states on the one journey, and native boot is either evidenced or blocked with the exact requirement recorded. S1's result must exist as a recorded ADR note — "seemed fine" is not a result.

  • Clean clone + README commands produce the export on a second machine (or a fresh container) — recorded in PR evidence
  • OG assertions pass for list and all detail pages; deliberate-failure demo shows them failing when the route is removed
  • Env guard fails fast on a missing variable (demo evidenced)
  • pnpm typecheck runs and reports zero errors on the skeleton (first real run = the evidence; no prior run is claimed)
  • Android boot evidenced, or blocker recorded with exact setup steps; iOS likewise
  • D-02 and D-03 ADRs updated with execution-time evidence and honest statuses (validated at most — never approved without the user)
  • No cloud accounts, no secrets, no real content, one journey only

Blocks progression if: S1 fails and no fallback decision is recorded (blocks Phase 03+ web assumptions and forces the D-03 alternative discussion now — by design); typecheck is not wired (every later phase inherits the legacy 455-hidden-errors failure mode, review §3); the states are missing (Phase 08's reliability work would build on a spinning foundation).
